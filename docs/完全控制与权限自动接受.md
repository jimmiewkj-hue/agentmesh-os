# 完全控制与 GUI 权限自动接受（2026-11-04）

## 1. 行为

WebUI 第 3 步新增 **完全控制** 复选框，**默认勾选**。

- 勾选：GUI Agent 在任务开始时被切到自己的完全访问模式；任务执行期间通过 **CDP DOM** 轮询权限确认弹窗，按弹窗中真实的“允许/始终允许/本次会话内始终允许”等按钮模拟用户接受。
- 取消：不切换 Agent 权限模式，不点击任何确认；确认留在 Agent 应用内，由用户手动处理。
- 全程不合成 OS 鼠标/键盘/剪贴板事件：只使用 CDP `Runtime.evaluate`、DOM `.click()`/`Input.dispatchMouseEvent`（renderer 级）、应用 deeplink 和本地数据库字段。

配置持久化在 `<项目>/.agentloop/config.json`：

```json
{"full_control": true}
```

API：

```text
GET  /api/settings                    -> {"full_control": true}
POST /api/settings/full_control       {"enabled": true|false}
```

执行请求 `ExecutionRequest.full_control` 由规划、任务、验证、汇总统一传递；预检接口 `/api/preflight` 也支持 `full_control`。

## 2. 各 Agent 的权限接口（实测）

### 2.1 Trae CN / Trae 1.107.1

| 形式 | 实测接口 |
| --- | --- |
| 权限模式 | 输入区按钮 `button[data-permission-mode-trigger="true"]`，`aria-label` 为当前模式 |
| 模式菜单 | `.permissionModePopover-*` / `.permissionModeContent-*`；选项 `.permissionModeItem-*`，名称 `.permissionModeItemName-*`：`手动审批` / `自动审批` / `完全访问` / `自定义` |
| 切到完全访问 | 点击菜单项“完全访问”；会弹出确认框 `启用完全访问？`，按钮 `取消` / `启用`（容器 `.dialog-*`，不是 `[role=dialog]`） |
| 自动接受 | 点击确认框中的 `启用`，回读 trigger 的 `aria-label` 必须为 `完全访问` |
| 残留权限卡 | watcher 识别可见权限容器中的 `始终允许` / `允许本次会话` / `允许一次` / `允许` |

真实测试（`logs/ui-e2e-20261104/trae-full-access-test.log`）：

```text
初始：完全访问
手动切到：手动审批
ensure_trae_full_access -> clicked 完全访问, confirm 启用
最终：完全访问
```

### 2.2 WorkBuddy 5.9.3

| 形式 | 实测接口 |
| --- | --- |
| 任务级权限 | `workbuddy://task?...&permissionMode=fullAccess`；`workbuddy.db` 回读 `permission_mode=fullAccess` |
| 输入区设置 | `.cr-permission-setting`，文本为 `允许完全访问` 或 `默认权限`；弹层 `.cr-permission-panel` 内开关 `input[role="switch"][aria-label="允许完全访问"]` |
| 文件安全确认 | 实拍到的弹窗文案：`读取文件命令询问规则，需要确认。` / `文件：...` / `当前命令：Read ...`；按钮：`允许读取`、`本次会话内始终允许`、`拒绝` |
| 自动接受 | watcher 优先点击 `本次会话内始终允许`，其次 `允许读取` / `允许执行` / `允许写入`；仅在可见权限容器内点击 |

说明：本机在测试中已对部分文件路径执行过“始终允许”，且 WorkBuddy 对任务使用 deeplink 的 `fullAccess`，因此后续普通读/写不再稳定复现弹窗。watcher 的点击逻辑在真实 WorkBuddy 渲染进程里用合成的“权限弹窗 DOM”验证过（`logs/ui-e2e-20261104/permission-cdp-click-test.json`：点击一次、弹窗移除）。真实任务 `P001` 的 `interface_verify` 回读 `permission_mode=fullAccess`。

输入区开关在部分会话中无法通过 DOM 重新打开（状态为 `默认权限`），本项目不依赖该开关：任务权限由 deeplink 固定为 `fullAccess`，残留弹窗由 watcher 接受。

### 2.3 Qoder CN 0.5.3

| 形式 | 实测接口 |
| --- | --- |
| 会话权限字段 | `%APPDATA%\com.qodercn.app.stable\main.sqlite` → `chat_sessions.permission_mode`；当前活动会话实测为 `bypassPermissions` |
| 模式取值 | 应用文案映射：`每次询问=acceptEdits`、`自动审批=auto`、`完全访问=bypassPermissions` |
| 确认弹窗 | 应用内文案：`高危操作`、`允许“{{toolName}}”？`、按钮 `拒绝` / `允许` / `允许一次`，建议项 `本次任务允许` / `始终允许` |
| 自动接受 | 任务开始前把当前 Qoder 会话的 `permission_mode` 写为 `bypassPermissions`；watcher 兜底点击 `始终允许` / `本次任务允许` / `允许一次` / `允许` |

`prepare_qoder_session(..., permission_mode="bypassPermissions")` 在执行前写入该字段并重启 Qoder；不是猜测的模型 API。

### 2.4 其他 Agent

- OpenCode / Claude Code / Gemini CLI / Codex CLI / Aider：非交互 CLI，适配器显式使用各自非交互参数；没有 GUI 确认弹窗需要自动接受。
- ZCode / DSH / Cursor：当前仅文件/会话接力，不自动执行，也没有可点击的权限确认接口。
- REA Studio：MCP `tools/call`，由 MCP 服务处理授权；本项目不越权调用。

## 5. 边界与风险

- “完全控制”会授予 Agent 与用户本人相当的本机操作权限（Trae 的确认框原文也明确提示：读写本地文件、执行终端命令、联网与扩展）。默认勾选是本次测试要求的便利选项；生产环境建议按任务关闭。
- watcher 只点击**可见的权限弹窗按钮**，不会点击普通 UI；短标签 `允许` 只在权限容器内生效。
- GUI 自动化仍运行在用户账户下，不是强沙箱；控制平面的任务 scope、Worktree 隔离、审批与回滚仍然有效。
- Qoder 的 `bypassPermissions` 写入需要该 Agent 有可恢复的会话；没有会话时 `prepare_qoder_session` 会返回明确错误，不会伪造成功。
- WorkBuddy 输入区开关在部分版本/会话状态下无法通过 DOM 重新打开；任务级 `permissionMode=fullAccess` 与 watcher 兜底是本项目采用的路径。
