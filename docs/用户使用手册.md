## 1. 产品是什么

AgentMesh OS 是一个本地优先的多 Agent 协同操作系统。它不是“主 Agent 指挥子 Agent”，而是：

```text
用户 → AgentMesh Controller（确定性控制平面）
        ├── Unified Memory
        ├── Task Scheduler
        ├── Capability Router
        ├── Cost Optimizer
        └── Human Governance
     → Context Bus
     → 本机所有 Agent（资源池）
```

- 用户指定一个主节点 Agent 和主模型，负责需求理解、任务拆分、关键决策与汇总；
- 子节点承担扫描、检索、实现、测试、调试等高 Token 消耗执行；
- 控制器同步结构化状态与成果摘要，不复制完整聊天；
- 文件修改在独立 Git Worktree 中发生，合并前必须通过验证与人类审批；
- 架构设计、验收确认、代码合并、发布上线必须由用户批准。

### 1.1 它不会做什么

- 不做第三方软件破解、逆向或 GUI 自动化；
- 不读取第三方 Agent 的私有隐藏状态，不写回它们的会话；
- 不把自然语言“已完成”当作验收；
- 不自动选择“全球最强模型”；
- 不自动部署/推送；发布审批只记录人类决定；
- 不支持非 Git 项目。

## 2. 安装与初始化

### 2.1 检查环境

```powershell
python --version    # 需要 >= 3.10
git --version
node --version      # 可选，仅 Web 前端调试
```

### 2.2 安装依赖

```powershell
cd j:\qoder\agent-hub
python -m pip install -r requirements.txt
python -m pip install -e .          # 可选：安装后可在任意项目目录运行 agentmesh
```

### 2.3 初始化项目（Web 推荐 / CLI 兼容）

**方式 A：单一 Web 入口**

```powershell
python -m agentloop_hub serve --port 8787
```

打开 <http://127.0.0.1:8787>，在“指挥中心 → 项目目录”：

1. 输入一个目录路径（可以是尚不存在的新目录）；
2. 可选填写项目名称；
3. 点击“初始化项目”。

控制端会自动创建目录、执行 `git init`，若目录原本为空还会创建一个初始 commit，然后打开项目并探测 Agent。

**方式 B：CLI**

```powershell
cd <你的 Git 项目>
python -m agentloop_hub init
python -m agentloop_hub status
python -m agentloop_hub doctor
```

`init` 会：

- 创建 `.agentloop/` 工作空间与 `state.db`；
- 探测本机 Agent 与模型清单；
- 写入项目索引与代码结构记忆；
- 记录 Agent 软件版本；
- 把 `.agentloop/` 与 `.agentloop-task/` 加入 `.git/info/exclude`。

CLI `init` 只支持已有 Git 项目；空目录或非 Git 目录请使用 Web 控制台初始化。运行仍要求 Git，因为 Worktree/Patch 隔离依赖它。

## 3. 核心概念

### 3.1 七个模块

| 模块 | 作用 |
| --- | --- |
| Agent Connector | 统一 `{agent_id, capability[]}`，把 14 类本机 Agent（含 REA MCP）接入资源池 |
| Unified Memory | 消息、任务、项目索引、代码结构、知识、决策、工作流、偏好 |
| Context Bus | Prompt/Response/文件变更/任务状态/知识/工作流统一事件流 |
| Task Scheduler | 依赖 DAG、优先级、重试、熔断、并发 |
| Capability Router | 能力门槛 + 成功率/验证/速度/成本评分，自动选 Agent |
| Cost Optimizer | 上下文压缩、语义缓存、结果复用、Agent Benchmark |
| Human Governance | 架构/验收/合并/发布四道人类门禁 |

控制端的扩展能力不属于七个核心模块，但围绕它们提供单一入口：

| 扩展 | 作用 |
| --- | --- |
| Agent Model Catalog | 真实探测 + 用户登记模型；主/子 Agent 分别选配 |
| Agent Version Ledger | 版本/能力指纹台账；Agent 升级后能力退化提示漂移 |
| Unified Web Console | 项目初始化、Prompt、主/子 Agent 模型、审批运行、SSE 实时监控 |
| MCP Adapter | 接入 REA Studio 等本地 MCP 服务；真实 `tools/list` / `tools/call` |

### 3.2 任务状态

```text
draft → pending_approval → queued → running
running → waiting_agent / waiting_user / verifying
verifying → completed / failed / blocked
failed → queued（重试）
blocked / paused → queued（恢复）
queued/running/waiting_* → canceled
```

运行状态：

```text
planning → pending_approval → ready → running
→ waiting_user / pending_acceptance / pending_merge
→ merging → completed → released
失败分支：failed / paused / canceled
```

### 3.3 接入等级

- L0 人工接力：复制提示词和结果。
- L1 文件协同：共享目录与任务文件。
- L2 结构化任务协同：任务包 + 成果包（GUI Agent 需用户触发）。
- L3 会话/CLI 协同：可非交互执行或读取会话。
- L4 原生双向控制：本期不承诺。

### 3.4 五级同步

| Level | 内容 |
| --- | --- |
| 1 | 消息 / 历史会话摘要 |
| 2 | 任务状态 |
| 3 | 上下文：项目索引 / 代码结构 |
| 4 | 知识 / 决策 |
| 5 | 工作流状态 |

### 3.5 结果同步

子节点可以扫描 100 个文件，但只把结构化 digest（摘要、发现、变更文件、测试、风险、未解决项）同步给主节点或依赖任务。完整成果保留在任务账本中。

## 4. 五分钟跑通第一条闭环

```powershell
cd <Git 项目>

# 1) 初始化
python -m agentloop_hub init
python -m agentloop_hub connectors
python -m agentloop_hub agents

# 2) 指定主节点与主模型
python -m agentloop_hub main set opencode --model opencode/deepseek-v4.1-flash-free

# 3) 单一入口：目标 → 计划
python -m agentloop_hub ask "修复 calc.py 中的加法错误并补充测试"

# 4) 如计划含 architecture 任务，先批准架构审批
python -m agentloop_hub approval list
python -m agentloop_hub approval approve <architecture_approval_id>

# 5) 批准计划
python -m agentloop_hub plan approve <plan_id>

# 6) 执行
python -m agentloop_hub run start <run_id> --parallel 2

# 7) 验收确认
python -m agentloop_hub approval list
python -m agentloop_hub approval approve <acceptance_approval_id>

# 8) 合并
python -m agentloop_hub approval approve <merge_approval_id>

# 9) 发布审批（可选）
python -m agentloop_hub release <run_id>
python -m agentloop_hub approval approve <release_approval_id>

# 10) 审计与成本
python -m agentloop_hub audit --verify
python -m agentloop_hub costs
python -m agentloop_hub bus verify
```

## 5. Agent 接入与主节点

### 5.1 自动发现

```powershell
python -m agentloop_hub discover
python -m agentloop_hub connectors --json
```

本机矩阵（2026-11-03）：

| Agent | 存储/CLI | 等级 |
| --- | --- | --- |
| Trae / Trae CN | `%APPDATA%/<Trae\|Trae CN>/ModularData/ai-agent/database.db` | L2 |
| Qoder / Qoder CN | `~/.qoder{,-cn}/projects/**/*.jsonl` | L2 |
| ZCode | `~/.zcode/cli/rollout/model-io-sess_*.jsonl` | L2 |
| WorkBuddy | `~/.workbuddy/projects/**/*.jsonl` | L2 |
| DeepSeek Harness | `~/.dsh/sessions/**/*.jsonl.zstd` | L2 |
| OpenCode | `opencode run --format json` | L3 |
| Claude Code | `claude -p`（安装才启用） | L3 |
| Gemini CLI | `gemini -p`（安装才启用） | L3 |
| Codex CLI | `codex exec`（安装才启用） | L3 |
| Aider | `aider --message`（安装才启用） | L3 |
| Cursor | `cursor` / 安装目录 | L1-L2 |
| REA Studio | 项目级 `.mcp.json` | L2（MCP） |

模型清单会自动从 CLI、会话事件与 Agent 自己的 provider/settings 配置中提取：

```powershell
python -m agentloop_hub models
python -m agentloop_hub models --refresh
```

2026-11-03 本机实测：14 个 Agent、93 个模型；其中 OpenCode 40、DeepSeek Harness 40、ZCode 10、Qoder 1、WorkBuddy 1。Trae 的模型状态存放在加密数据库，系统不会猜测，允许用户手动登记。

### 5.2 手动注册 CLI Agent

```powershell
python -m agentloop_hub agent add `
  --id my_agent --name "My Agent" --product "My Agent" `
  --adapter cli --level L3 `
  --command python `
  --config-json '{"command":["python","my_agent.py"],"args":["{prompt_file}"],"prompt_mode":"file"}'
```

Agent 必须遵守：读取任务包 → 在 workdir 执行 → 写入 `result_path` 的 17 字段 JSON。

### 5.3 主节点

```powershell
python -m agentloop_hub main set <agent_id> --model <model>
python -m agentloop_hub main show
python -m agentloop_hub main history
```

主节点负责：

- `ask` / `plan request`：需求理解与任务拆分；
- 运行结束后的汇总与合并建议；
- 交接包中的目标、约束、决策与风险。

主节点默认不参与子任务执行；Capability Router 会排除主节点。

### 5.4 主/子 Agent 模型选配

Web 指挥中心第 3 步提供：

- 主 Agent 下拉框：选择负责规划/汇总的 Agent；
- 主模型下拉框：只列出该 Agent 的真实模型；也可手填；
- 子 Agent 列表：每个 Agent 一个模型下拉框 + 手填输入 + 保存按钮。

选配结果持久化：

- 主模型 → `main_nodes.model`；
- 子模型 → `agents.extra.selected_model`；
- 手动输入的未知模型 → `agent_models.source=user`。

执行器与规划器优先使用 `selected_model`，其次主节点模型，最后才回退到 Agent 默认模型。

版本台账：

```powershell
python -m agentloop_hub versions --status
python -m agentloop_hub versions --agent zcode
```

当某个 Agent 升级后适配器类型变化或能力集合减少，状态会变为 `drift`，控制台“Agent 版本”页给出复核建议。

## 6. 规划与任务图

### 6.1 生成计划

```powershell
python -m agentloop_hub ask "目标"
# 等价于
python -m agentloop_hub plan request "目标"
```

主节点写出 `plan.json`。非法计划会自动请求一次修复。

### 6.2 导入/修改计划

```powershell
python -m agentloop_hub plan import plan.json
python -m agentloop_hub plan show <plan_id>
```

计划任务字段：

```json
{
  "task_id": "T001",
  "title": "扫描 calc.py",
  "type": "analysis",
  "objective": "读取并报告加法实现问题",
  "suggested_agent": "opencode",
  "dependencies": [],
  "scope": ["calc.py"],
  "out_of_scope": ["README.md"],
  "expected_outputs": ["summary"],
  "acceptance_criteria": ["指出具体行号"],
  "verification_commands": [],
  "token_budget": 30000,
  "time_limit_minutes": 30,
  "retry_limit": 2,
  "risk_level": "low",
  "approval_policy": "auto",
  "priority": 5
}
```

`type` 可选：analysis / implementation / verification / documentation / review / architecture。

`priority` 0..10，越大越先执行；依赖优先于优先级。

### 6.3 架构审批

如果计划包含 `type=architecture` 任务：

1. `plan import/request` 会返回 `architecture_approval_id`；
2. 必须先 `approval approve <architecture_approval_id>`；
3. 然后才能 `plan approve`；否则返回 `approval_required`。

## 7. 调度、路由与执行

### 7.1 启动运行

```powershell
python -m agentloop_hub run start <run_id> --parallel 2
python -m agentloop_hub run resume <run_id>
python -m agentloop_hub run status <run_id>
```

调度规则：

- 只派发依赖已完成的 `queued` 任务；
- 同层按 `priority` 降序；
- 前置失败/取消 → `blocked`；
- 连续最终失败达到阈值 → 熔断并暂停剩余任务；
- `max_parallel` 控制并发（默认 2）。

### 7.2 能力路由

```powershell
python -m agentloop_hub route rank --task-type implementation
python -m agentloop_hub route task <task_uid>
python -m agentloop_hub route scores
python -m agentloop_hub route decisions --run <run_id>
```

评分：

```text
能力 0.40 + 成功率 0.25 + 验证通过率 0.15 + 速度 0.10 + 成本 0.10
+ 访问等级 0.02 + 计划建议 0.03
```

主节点被排除；不可用/离线/能力不足的 Agent 会记录拒绝原因。

### 7.3 waiting_user

当任务需要人工审批、预算审批、或 GUI Agent 等待接力时：

- `run status` 显示 `waiting_user`；
- `approval list` 查看待审批；
- GUI 接力：在 `relay/<task>/inbox/prompt.md` 执行，把结果写入 `relay/<task>/outbox/result.json`；
- 回填：`task submit-result <uid> --file result.json`；
- 继续：`run resume <run_id>`。

#### WebUI 收尾通道（2026-11-08）

GUI Agent 在应用内完成但适配器超时、主节点在应用内写出汇总、或节点卡死需要换模型时，
控制台提供与 API 等价的按钮，不必手工调接口：

- **采纳已有成果**：任务详情「尝试记录」或链路节点的「采纳成果」→ 选择有 `result.json` 的尝试；
  控制平面会把该尝试切换为活动成果并进入验证，**不会重发请求**。
- **人工提交成果包**：任务详情填写 JSON/路径时自动带上"关联尝试"的 `attempt_id`；
  API 仍强制活动尝试必须携带 `attempt_id/request_id`。
- **回填汇总 JSON**：运行卡片或阻塞弹窗的「回填汇总 JSON」→ 粘贴 JSON 或填项目内路径
  （路径必须位于项目目录内），校验通过后继续轮次/验收判定。
- **停止当前尝试并改绑**：运行中的节点也可「编辑绑定」，勾选"停止当前尝试并改绑"后保存；
  节点转为 blocked 并提示重试，旧尝试的晚到结果会被隔离，不会覆盖新绑定。
- **导入已有计划**：页内模态框（粘贴 JSON 或路径），不依赖浏览器 `prompt()`。
  粘贴内容允许带 ```json 代码围栏；文件可用 BOM/UTF-8；相对路径按工作区根目录解析；
  读取失败、JSON 解析失败、计划校验失败分别给出可操作报错。

#### 计划阶段等待与自动接收（2026-11-11）

主节点是 GUI Agent（Trae/WorkBuddy）时，规划请求可能以 `waiting_user` 返回
（模型菜单未就绪、工作区切换、需要人工点击发送等）。此时：

- 控制平面在该计划目录写入 `watch.json` 并启动**持久监视**：Agent 之后写出
  `plan.json`（哪怕几小时后、哪怕服务重启过），会自动走校验/协作契约/审批链，
  计划变为 `pending_approval` 并通过总线通知 WebUI 刷新；监视默认保留 7 天
  （`plan_watch_seconds` 可配）。
- WebUI 的「等待主节点 UI 执行」卡片显示计划号、应用内操作指引与实时检测状态，
  并提供「导入该计划 JSON」按钮（已预填结果文件路径）；检测到完成后自动载入待审批。
- 监视器**不会**自动发起新的 Agent 生成：计划校验失败只标记 `invalid` 并给出错误，
  由用户决定修复或导入；重新规划或手动导入会把旧监视标记为 `superseded`。
- `GET /api/plans/watches` 可查看全部监视记录（watching/completed/invalid/expired/superseded）。
- Trae 复用路径的工作区打开以「新出现的匹配标题 CDP 页面」为证据（纯文件夹窗口
  不会写 solo-lite 全局缓存），并把该页面固定用于模型选择、发送与回读；
  Trae 全局会话状态不维护 `messageIds/assistant_task_status` 时，回读用
  DOM 完成摘要（思考用时）+ 完整结果文件 + 会话稳定作为完成证据；
  回读超时但计划文件已写出时按 salvaged 接收，不丢弃已完成的工作。

#### 同 Agent 会话续接与合成冲突阻塞（2026-11-09）

- 同一 Agent 的后续链路节点默认接续上一节点的会话与工作树：WorkBuddy 切回原会话、
  OpenCode 用 `--session <id>`、ZCode 用 `--resume <id>`；不同 Agent 才新开会话；
  首节点与主节点规划/汇总仍是独立会话；模型变化时保留工作树但新开会话。
- 当其他 Agent 的上游补丁与该 Agent 的会话工作树冲突时，节点转为 `waiting_user`
  （错误以 `SESSION_COMPOSE_CONFLICT:` 开头），**原会话保留，不会静默新开对话**：
  1. 按错误提示在该会话工作树手动执行 `git apply --3way <补丁路径>`，解决冲突后 `git` 提交；
  2. 点「继续运行」或该节点的「重试节点」，即在原会话、原工作树中继续；
  3. 不想手动解决时，也可「编辑绑定」改换该节点的 Agent/模型。
- 该阻塞发生在发送请求之前：不消耗 token、不产生尝试记录，重排只会重试合成。

#### 控制平面联网检索与 dsh 接入（2026-11-10）

- **联网检索工具**：控制平面内置无 key 搜索（DuckDuckGo Lite），具备 terminal 的子节点可直接调用：

```powershell
python -m agentloop_hub search "关键词" --max-results 5
# 或 HTTP：GET /api/tools/web_search?q=关键词
```

  输出 JSON（title/url/snippet，url 已解码为真实站点）。能力清单为 terminal Agent 派生 `web_search`
  （hub 工具中介，非 Agent 原生浏览；显式 `web_search=false` 仍优先禁用）。任务包会自动注入调用指引；
  检索失败如实写入 risks，不伪造结果。
- **dsh（DeepSeek Harness）已升 L3**：通过桌面安装自带的 headless profile 以 Electron Node 模式
  零输入执行（`--profile headless --json`），支持 `--session-id` 会话续接；模型经 launcher `--patch`
  覆盖 `agent-default-model`（`--model` 非合法选项）。适配器自动从 `~/.dsh/.credentials.yaml` 凭据服务
  加载 provider 密钥（如 DEEPSEEK_API_KEY）入执行环境，无需手工导出；缺凭据时快速失败
  `MISSING_CREDENTIAL` 并归类鉴权降级，不静默挂起。已真实端到端跑通（写出 result.json、usage 解析、续接）。

#### MCP Server：记忆与搜索 pull（2026-11-10）

任意支持 MCP 的 Agent 可主动连接控制平面（只读）：

```powershell
python -m agentloop_hub mcp-serve --project <项目根目录>
```

在 Agent 的 MCP 配置中把它作为 stdio server 添加（command=python，args 同上）。暴露工具：

- `memory_bootstrap(agent_id?, scope?)`：项目状态/主节点/近期运行（启动时拉取）
- `memory_search(keyword, limit?)` / `memory_list(type?, status?, limit?)`：统一记忆检索
- `web_search(query, max_results?)`：控制平面联网检索
- `task_state(run_id?)`：当前运行与任务状态
- `bus_events(after_seq?, limit?, topic?, kind?)`：只追加上下文总线事件读取（游标）

stdout 为 MCP 通道，服务不打印其他内容；工具全部只读。

### 7.4 重试与取消

```powershell

python -m agentloop_hub task cancel <uid>
```

重试会复用已分配的 Agent 以保持稳定性；Radical 失败会走熔断。

## 11. 成本优化与预算

### 11.1 预算

```powershell
python -m agentloop_hub budget set 200000

```

预算不足时创建预算审批；批准后继续，不静默降级。

### 11.2 成本优化

```powershell
python -m agentloop_hub cache stats
python -m agentloop_hub cache clear
python -m agentloop_hub benchmark
python -m agentloop_hub costs
```

策略：

- 上下文压缩：超出 Token 上限自动裁剪；
- 精确缓存：任务条件 + 文件树哈希完全一致；
- 语义缓存：只读任务 + 同一文件基线 + 意图相似度（**默认本地 EmbeddingGemma 向量余弦 ≥0.85**；
  模型/依赖不可用时回退词袋 Jaccard ≥0.82，结果标注 `method`）；
- 中间结果复用：依赖任务只接收上游 digest；
- Agent Benchmark：成功率、验证通过率、平均 Token/成本/耗时；
- 节省账本：`savings_ledger` 记录每笔节省。

可写任务永不自动复用成果。

### 11.3 美元价格表与节省度量（2026-11-10）

- 价格以**用户配置为权威**：在项目或全局 `config.json` 的 `pricing` 填入官方价格表/账号账单单价
  （USD/百万 token，input/output），即可度量美元节省：

```json
{ "pricing": { "deepseek-v4-pro": { "input": 0.66, "output": 1.98 } } }
```

- 内置 `DEFAULT_PRICING` **仅含无歧义的免费模型（0）**；付费模型价格**不臆测**（公开来源按日期/分时
  互相矛盾，旧别名 deepseek-chat/reasoner 已退役），未配置时记为 **unknown 而非 free**。
- 压缩/中间结果复用/精确缓存的节省按 **input 价**估算美元并入账（`cost_saved`），
  `costs`/WebUI 累计节省同时显示 token 与美元。
- 未知模型：美元记 0、token 仍入账，使用记录 `cost_known=False` 如实标注。美元为估算值，非精确账单。

### 11.4 真·语义缓存（本地嵌入，2026-11-10）

- 默认使用本机 EmbeddingGemma-2 向量（768 维；torch + transformers 加载，mean-pool + L2 归一化），
  只读任务在同一文件基线下按**意图余弦相似度 ≥0.85** 命中；嵌入只取 objective+验收条件，
  scope 由文件基线保证、任务类型单独过滤。
- 配置（项目/全局 `config.json`）：

```json
{
  "semantic_cache_backend": "auto",
  "embedding_model_path": "D:/llm/ai-stack/gemmaenbending/models/embeddinggemma-2",
  "embedding_device": "cpu",
  "embedding_max_length": 512,
  "semantic_cache_embedding_threshold": 0.85
}
```

- `semantic_cache_backend`：`auto`（有模型则嵌入，否则回退）/ `embedding`（强制嵌入，不可用则回退并标注）/
  `jaccard`（强制词袋）。引用结果带 `method=embedding|jaccard`，不冒充语义。
- 模型首次加载约占 1.5 GB 内存、数秒；缺失 torch/transformers 或模型时自动降级，不阻断主链路。
- 真实效果（本机实测）：中文改写任务相似度 0.955，无关任务 0.688；缓存命中 0.958（`method=embedding`）。

```text
├── patches/
├── reports/
├── checkpoints/
├── handoffs/
├── relay/
├── conversations/
└── audit/
```

`state.db` v3 额外保存 `agent_versions`（版本台账）与 `agent_models`（模型目录及来源）。

备份：复制整个 `.agentloop/` 即可；`state.db` 使用 WAL 时可先停止服务。

清理：删除 `.agentloop/` 会丢失任务、审批、审计、记忆、总线与缓存；建议先导出记忆与审计。

移动项目：`.agentloop` 使用路径身份，移动后重新 `init` 会生成新 project_id；建议在旧路径完成结算后迁移。

## 24. 故障排查

按顺序查看：

1. `agentmesh doctor --json`：Git/DB/审计/总线/Agent/记忆。
2. `agentmesh status`：项目、主节点、预算、运行。
3. `agentmesh agents`：在线状态与能力。
4. `agentmesh task show <uid> --level raw`：日志与错误。
5. `.agentloop/tasks/<uid>/logs/agent.stderr.log`。
6. `agentmesh audit --limit 200`：最近动作。
7. `agentmesh bus list --correlation_id <uid>`：该任务信息流。

常见问题：

- 计划一直不完成：主节点是 GUI Agent，需在对应软件执行 `plan_request.md` 并写回 `plan.json`；
- 运行停在 `waiting_user`：查看 `approval list` 或接力 outbox；
- 成本为 0：模型未配置价格或 Agent 未上报 usage；
- 合并被拒绝：验收未通过、审批未批准、工作区有重叠修改、分支不一致或跨任务同文件冲突；
- 发布申请失败：运行未合并完成或验收未通过；
- 语义缓存未命中：任务可写、文件基线变化、意图相似度低于 0.82。

## 25. 安全边界与已知限制

已实现：

- 本地优先，不上传项目；
- 子任务独立 Worktree；
- scope/out_of_scope 与租约；
- 合并预检与回滚；
- 危险命令/高风险文件审批；
- 追加式审计与总线哈希链；
- 执行者不能自验；
- 架构/验收/合并/发布人类门禁。

不是强沙箱：Agent 进程以当前用户权限运行。

已知限制：

- GUI Agent 需人工触发；
- 外部 CLI 需登录/额度；
- 运行要求 Git；非 Git 目录可用 Web 控制台初始化，CLI `init` 会拒绝；
- Trae 等加密存储的模型清单无法自动读取，需用户手动登记；
- 版本漂移只提示不自动修复；
- 发布门禁不部署；
- 语义缓存是本地相似度，不是向量嵌入；
- P2：多电脑同步、团队权限、云端调度、GUI 自动化、会话写回、插件市场未实现。

## 26. FAQ

**Q1：`plan approve` 和 `approval approve` 有什么区别？**  
`plan approve` 是针对计划的快捷命令；底层会处理对应的 `plan` 审批。`approval approve` 可处理架构/验收/合并/发布/高风险/预算等任意审批。

**Q2：为什么 `plan approve` 报 `approval_required`？**  
计划含 architecture 任务，需先批准 `architecture` 审批。

**Q3：为什么运行停在 `pending_acceptance`？**  
主节点汇总已完成，等待用户验收确认。批准 acceptance 后才会生成 merge 审批。

**Q4：合并后运行状态是什么？**  
`completed`；只有再次批准 release 审批后才变 `released`。

**Q5：成果包字段到底多少个？**  
17 个必填字段；缺字段直接拒绝。

**Q6：为什么任务完成了但合并建议 reject？**  
汇总中的 `merge_recommendation` 由主节点根据验证结论、风险与未解决项给出；用户仍可拒绝或返工。

**Q7：能让多个 Agent 同时改同一文件吗？**  
不能。可写任务 scope 租约会阻止重叠；合并前还会检查跨任务 Patch 文件交集。

**Q8：如何让 GUI Agent 自动执行？**  
本项目不做 GUI 自动化。L2 接力需要用户在软件中执行并回填结果；L3 CLI Agent（OpenCode/Claude Code/Gemini/Codex/Aider）可自动执行。

**Q9：语义缓存安全吗？**  
只对只读任务、同一文件基线、相似意图生效；命中后仍走验证；可写任务永不自动复用。

**Q10：可以直接改 `state.db` 吗？**  
不建议。审计与总线是追加式；直接改状态会破坏哈希链，`doctor` 会报告失败。请使用 CLI/API。

**Q11：模型列表为什么有些 Agent 是空的？**  
只展示真实可观测的模型。Trae 的模型状态在加密数据库中，系统不会猜测；可在 Web 指挥中心手填模型名，来源会标记为 `user`。

**Q12：Agent 升级后控制台提示“能力漂移”怎么办？**  
打开“Agent 版本”查看变更明细（版本、适配器、能力增删、模型增删）；确认适配器配置是否仍可用，必要时回滚 Agent 或重新注册接入方式。控制台不会自动修改 Agent。
