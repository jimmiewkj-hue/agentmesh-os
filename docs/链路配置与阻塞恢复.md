# 链路配置、统一执行入口与节点阻塞恢复

- 版本：2026-11-05
- 适用范围：WebUI 指挥中心第 3.5 节「多 Agent 链路配置」、第 4 节「计划审批与运行」
- 结论先行：**3.5 只保存配置；第 4 步批准计划 + 开始执行是唯一执行入口；节点需要人工提交/审批时，链路阻塞、WebUI 弹窗，节点完成后自动继续。**

---

## 1. 用户操作路径（唯一正确顺序）

```text
① 项目目录 → 浏览… → 初始化项目
② 输入 Prompt → 生成任务计划（主 Agent 产出 N 个任务，计划进入待审批）
③ 主 / 子 Agent 与模型 → 保存
③.5 从计划载入阶段（自动 N 个阶段）→ 每阶段选择 Agent / 真实模型 / 任务类型
    → 保存链路配置（待审批）
④ 待审批 → 批准计划 → 最近运行 → 开始执行
```

- **阶段数量 = 计划任务数量**，不再固定 3 个；没有计划时可「添加阶段 / 删除阶段」创建独立链路。
- **3.5 保存不会批准计划、不会创建运行、不会启动任何 Agent 应用。**
- 第 4 步「开始执行」才会创建 Worktree、发送任务、拉起 GUI Agent。

## 2. 问题 1：页面刷新后链路配置被重置

### 根因

1. 旧实现把链路阶段写死为 `CHAIN_STAGES` 三个默认值；`render()` 每次刷新都用默认值重建 DOM。
2. 用户改动只存在于 DOM，没有写入任何持久层；任意一次 `refresh()` 都会覆盖。
3. 静态 `app.js` 没有版本参数，浏览器可能缓存旧脚本；旧脚本里残留的 `CHAIN_STAGES` 引用会抛
   `ReferenceError: CHAIN_STAGES is not defined`，导致 onchange/onclick 静默失效。
4. 刷新可能在用户编辑途中完成（定时器在获得焦点前已经排好），直接重建 select。

### 修复

- 服务端草稿：`GET/POST /api/chain/draft`，保存在 `<项目>/.agentloop/chain-draft.json`，
  包含 `plan_id / goal / policy / stages[]`。
- 浏览器草稿：`localStorage["agentmesh.chain.<project_id>"]`，每次字段变更立即写入。
- 每次 onchange/oninput 调用 `chainFieldChanged()`：
  - 从 DOM 收集阶段 → 更新 `state.chainDraft` → localStorage → 700ms 防抖 POST 服务端。
- `renderChain()` 在以下情况**不重建**：
  - 当前焦点仍在 `#chainStages`、`#chainGoal`、`#chainPolicy` 内；
  - 状态草稿已水合且阶段值一致。
- `index.html` 给脚本加版本参数（`app.js?v=20261105-7`），避免旧缓存。
- 增加页面级 `#jsError` 提示条，脚本异常不再静默。

### 实际验证（2026-11-05）

- 3 阶段独立链路：把阶段 1 改为 `workbuddy / GLM-5.3-Flash / review`，刷新后仍是 3 阶段且值不变。
- 真实计划 `plan_9c0dba963c88`（6 个任务）：
  - 生成计划后 3.5 自动载入 **6 个阶段**，与计划任务数一致；
  - 把阶段 1 改为 `workbuddy / GLM-5.3-Flash`，刷新后仍为 6 阶段且保持该值；
  - 保存后计划任务 `T001` 的 `suggested_agent/model` 确认为 `workbuddy / GLM-5.3-Flash`。

## 3. 问题 2：3.5「配置并运行」与第 4 步审批的逻辑冲突

### 根因

旧 `configure_chain(start=true, approve=true)` 会：

1. 另建一个计划（不是第 2 步生成的计划）；
2. 自动批准架构与计划；
3. 立即创建运行并启动 Agent。

于是用户在 3.5 点「配置并运行链路」时，一个**隐形的第二计划**已经开始执行；
第 4 步看到的仍是第 2 步那个待审批计划，形成两个计划、两个入口。

### 修复后的契约

| 操作 | 行为 |
| --- | --- |
| 3.5「保存链路配置（待审批）」 | 绑定到当前待审批计划；只更新计划的 `suggested_agent / model / type`，不创建运行 |
| 第 4 步「批准计划」 | 校验架构门禁 → 计划置为 approved → 创建 `ready` 运行与任务 |
| 第 4 步「开始执行」 | 唯一执行入口：创建 Worktree、调度任务、拉起 Agent |
| 3.5「预检并打开 Agent」 | 独立、显式的应用预检；会提示将重启桌面应用 |

服务端 `POST /api/chain` 新增：

```json
{
  "plan_id": "plan_xxx",
  "stages": [{"task_id": "T001", "agent_id": "workbuddy", "model": "GLM-5.3-Flash", "type": "analysis"}],
  "save_only": true,
  "start": false,
  "approve": false
}
```

- `plan_id` 存在：只允许 `pending_approval` 计划；阶段数必须与计划任务数一致；按 `task_id` 绑定。
- 没有 `plan_id`：创建独立链路计划，默认仍为 `pending_approval`，同样走第 4 步门禁。
- 独立链路导入后，会再次写回用户选择的 Agent/模型/类型，覆盖协作契约的自动改派
  （`chain.pins_applied` 审计），保证 3.5 的显式选择优先。

### 实际验证

- 保存 4 阶段链路：`/api/runs` 数量不变，`/api/plans` 新增 `pending_approval` 计划。
- 保存 6 阶段真实计划：`plan_9c0dba963c88` 保持 `pending_approval`，最新运行仍是旧的 `run_105...`。
- 只有点击第 4 步「开始执行」后，运行状态才从 `ready` 变为 `running`。

## 4. 问题 3：WorkBuddy / Trae 闪退与节点阻塞

### 根因（来自真实日志，不是猜测）

`D:\temp\.agentloop\tasks\run_1ab2b6aeb9e4_R2_T002\gui\gui.log`：

```text
23:35:14 submit_retry_deeplink  deeplink 未把任务文本填入输入框（只有占位符）
23:35:18 workbuddy_restarted_for_prefill  ok=true  reused=false
23:35:22 submit_retry_deeplink  ...
23:35:25 workbuddy_restarted_for_prefill  ok=true  reused=false
23:35:32 workbuddy_restarted_for_prefill  ok=true  reused=false
```

- `submit_composer_via_cdp` 看到欢迎页占位符（25 字）就立即判失败，**没有等待本次 marker**；
- 适配器随后 `taskkill /F /IM WorkBuddy.exe` 并重启，20 秒内 3 次；
- Trae 执行路径固定 `force_restart=True`，每次任务都杀进程再启动。

用户在屏幕上看到的就是「刚填完输入框就闪退」「Trae 明明在运行也无故闪退」。

### 修复

1. **预填等待 marker**：`submit_composer_via_cdp` 在 `prefill_timeout` 内等待带本次 marker 的文本，
   占位符不再触发失败。
2. **预填失败不重启进程**：重新发一次深链接；仍失败则用
   `send_visible_prompt_via_cdp` 选中可见输入框写入并点击应用自己的发送按钮。
3. **Trae 复用**：`ensure_trae_cdp(force_restart=False)`；CDP 存活时只通过 Trae 自己的 CLI
   `--folder-uri` 请求打开目标工作区，绝不杀进程。
4. **应用未运行才启动**：进程不存在时启动带 `--remote-debugging-port` 的实例，这是安全动作。
5. **应用运行但无 CDP**：返回 `APP_RESTART_REQUIRED`，不自动杀进程；WebUI 弹窗让用户点击
   「重启 Agent 接口」。
6. **优雅重启**：`control/apps.graceful_close` 先 `taskkill /IM`（WM_CLOSE），等待 12s，
   仍未退出才 `/F`；关闭方式写入 GUI 日志与审计。
7. `APP_RESTART_REQUIRED` 加入 `GUI_ERROR_CODES`，不再被改写为 `GUI_UNSUPPORTED_PLATFORM`。

- Trae 第 1 节点（`run_105f7c6bf49e:CHAIN01`）执行前后 PID 均为 `58376`；
  GUI 日志 `cdp_ready reused=true`，无重启。
- WorkBuddy 运行中无 CDP 时：
  - 任务状态 `waiting_user`，运行状态 `waiting_user`；
  - WorkBuddy PID 保持不变（未被杀）；
  - 浏览器标题变为「⚠ 链路阻塞」，右侧弹窗列出节点、原因、处理按钮；

## 5. 阻塞与恢复语义

### 触发条件

- GUI 节点在**发送成功之前**失败：`APP_RESTART_REQUIRED`、`GUI_SEND_FAILED`、工作区/模型接口失败等；
- 发送按钮被禁用、需要人工在应用内点击发送或完成审批。

### 数据流

```text
Adapter._begin_manual()
  → 写 <task_dir>/manual-action.json
  → request.notify("manual_action_required")
  → Runner：task=waiting_user，run=waiting_user，audit + bus(manual_action)
  → /api/overview.manual_actions → WebUI 弹窗
```

- 手动提交场景：适配器延长 transcript `send_timeout`（默认 1800s），继续等待同一个会话；
  用户在应用里点击发送后，reader 收到 marker 与完成回复 → `manual_action_resolved`
  → 任务继续验证 → 依赖节点自动调度。
- 应用重启场景：适配器立即返回 `waiting_user`；用户点击「重启 Agent 接口」后，
  WebUI 调 `POST /api/agents/<id>/interface/restart` → `retry` → `resume`。
- Runner 的 `_active_tasks` 防止「重试节点」与仍在等待的适配器重复执行；
  `resume` 只重新排队非活动节点。
- 运行恢复时清空 `blocked_reason/error`，避免 UI 残留旧阻塞原因。

### 实际验证

- 真实链路 `run_105f7c6bf49e`：CHAIN02 → `waiting_user`，CHAIN01 已完成；
- 重启接口后自动恢复为 `running`，不重复执行 CHAIN01；
- 确定性集成测试 `test_blocked_node_resumes_and_next_node_runs`：
  - 节点 B001 阻塞时 B002 保持 `queued`；
  - 释放后 B001 `completed`、B002 自动启动并 `completed`；
  - `blocked_reason` 清空。

## 8. 已知边界

- WorkBuddy 模型/网络侧仍可能长时间不返回（本轮真实链路 CHAIN02 在 02:09:39 发送，
  02:20:16 才返回 69 个事件，超过 600s stall 阈值）。这是上游 Agent 行为，
  与控制平面重启缺陷是两件事；后续重复阻塞/恢复测试中 CHAIN02 在约 15s 内完成并通过验证。
- `open_trae_workspace` 的 CLI 打开工作区请求可能 20s 内未登记（GUI 日志会记录
  `workspace_open.ok=false`），后续 `set_trae_workspace` 与 `verify_trae_session` 仍会完成绑定；
  若最终校验失败，节点会阻塞而不是静默换 Agent。
- 重启桌面应用是用户可见动作，只在用户点击「重启 Agent 接口」或显式预检时发生；
  执行路径默认绝不自动杀进程。

## 9. 2026-11-05 第二轮真实测试暴露的问题与修复

### 9.1 T001 显示 completed，但 WorkBuddy 仍在运行，T002 被并行启动

真实日志 `D:\temp\qingmingshanghetu\.agentloop\tasks\run_35af3337a1ee_T001\gui\gui.log`：

```text
05:02:28 prompt_submitted
05:08:29 reply_received (91 events, 938 chars)
05:08:34 T001 completed，T002 于 05:08:34.745 开始
```

WorkBuddy transcript 显示 T001 在 05:08:29 已写入 `result.json`，但继续做最终自检和
memory 写入，直到 05:09:12 才结束。旧逻辑只要 `result.json` 可解析就返回，GUI 锁立即释放，
T002 的 deeplink 随即打开第二个 WorkBuddy 任务。

修复：

- `WorkBuddyReader.wait_reply` 在 result file ready 时：
  - 若 DB session 仍为 `working/running/pending`，继续等待；
  - 只有 DB `completed`，或（非 working 且 result/transcript 静默 ≥
    `workbuddy_result_settle_seconds`）才返回；
  - DB `error/cancelled` 立即抛错，不再等待。
- `last_is_final` 分支同样在存在 result-file 契约时拒绝 working 状态。
- Adapter 在 WorkBuddy 新任务前查询 `active_sessions()`（DB 中 status=working 且最近有活动）；
  有活动会话先等待 `workbuddy_active_wait_seconds`，超时返回 `APP_BUSY` 阻塞，
  不再静默打开第二个任务。
- 实测 `run_6a0246d278b9`：S001 session DB 14:12:41 completed → adapter 14:12:42 返回
  → S002 14:12:47 才创建，**没有重叠**。

### 9.2 T002 实际完成却被判 failed：scope 与验证命令不是可执行格式

真实计划 `plan_8d8ed94af285` 的 T002：

```text
scope: 新增 qingming-3d/src/scene/assets/**（materials.js、bridge.js、...）
verification_commands:
  Get-ChildItem D:\temp\qingmingshanghetu\.agentloop\planning\plan_8d8ed...\workspace\qingming-3d\src\scene\assets
```

旧 verifier 把整句中文当 glob，报“修改超出范围”；`Get-ChildItem` 又由 cmd.exe 执行而失败；
`git -C D:\temp\...` 也检查了错误的工作区。

修复：

- `models.normalize_scope_entries()`：从自然语言中提取路径/glob 与文件 token；
  裸文件名按 basename 匹配任意目录；相对目录/glob 会补上条目中的项目前缀。
- `models.normalize_verification_commands()`：
  - `.agentloop/planning/<plan>/workspace` 与 `.agentloop/runs/<run>/workspace`
    绝对前缀替换为任务工作区；
  - `git -C <绝对路径>` 改为 `git`（verifier 的 cwd 就是任务 Worktree）；
  - 去掉 `.\` / `./` 前缀。
- `process_runner.run_command()`：检测 `Test-Path/Get-ChildItem/Select-String/...`，
  通过 `powershell -NoProfile -NonInteractive -Command` 执行。
- Verifier 在运行时再次规范化，因此**旧计划上的重试**也生效。
- 实测 T002-like 任务 `run_6a0246d278b9:S002`：
  新建 `probe.md` 成功，scope `qingming-3d/src/scene/assets/probe.md` 通过，
  三条验证命令（PowerShell 路径、Test-Path、Select-String）全部通过，`verification=passed`。

| 层 | 默认值 | 作用 |
| --- | --- | --- |

### 16.1 为什么“暂停”停不下来

`pause_run` 只把运行置 paused：**当前 Agent 回合会继续跑完**，失败后仍可能进入重试队列，

  这些命令不会退出，旧逻辑会等到 `verify_timeout_seconds=900` 后判失败，
  导致节点长时间停在 `verifying`。
- 现在 `process_runner` 会识别常驻命令：
  - 只运行 `verify_server_probe_seconds`（默认 15s）；
  - 从输出中识别 loopback URL / listening / Ctrl+C，判定“已成功启动”，随后结束进程；
  - 验证报告增加 `server_check`，正常启动的服务器记为 passed，而不是 failed；
- `verify_timeout_seconds` 默认调整为 180s；
- `_finish_verification` 增加异常兜底，验证过程异常会把节点置 failed 并记录
  `task.verification_error`，不会永久停留在 `verifying`；
- 真机 T003 复验 38.2s 完成，`server_check=passed`、`unit_tests=passed`，
  任务 `completed/warning`；全量测试 **320 passed**。
