# 多轮对话与完成判定

本文记录 AgentMesh OS 如何判断一轮多 Agent 协作是否真正满足用户目标，以及未满足时如何自动开始下一轮。设计参考了本机可获取的 opencode 1.19.5 与 DeepSeek Harness（DSH）源码/安装包。

## 1. 问题

原实现中，一轮任务全部执行完后由主节点写 `summary.json`。只要主节点给出 `merge_recommendation=reject`，控制平面就进入验收门禁并结束运行；即使 `next_actions` 已经明确列出可修复项，也不会再规划、再调度子 Agent。表现就是：

```text
规划 -> 执行 -> 主节点审阅“未通过” -> 运行结束
```

用户需要的是：

```text
规划 -> 执行 -> 主节点审阅“未通过” -> 带着未解决项重新规划 -> 再执行 -> 再审阅 -> 通过 / 重复卡死 / 轮次上限
```

## 2. 参考实现分析

### 2.1 opencode：回合由工具调用和待处理输入驱动

参考版本：`opencode-ai@1.19.5`；源码取自 `anomalyco/opencode` 的 `dev` 分支。

关键路径：

- `packages/core/src/session/runner/llm.ts`：`drain()` 外层循环，每个 step 结束后由 `runStep()` 返回 `needsContinuation`，为真继续下一个 step，否则会话进入空闲。
- `packages/core/src/session/runner/step.ts`：把 step 结果映射为 `Completed/Continue/OutputLimit/Compacted/...`。
- `packages/core/src/session/runner/publish-llm-event.ts`：`needsContinuation` 的计算是

  ```text
  本轮存在本地执行的 tool call（called 或 settled）=> 需要继续
  ```

- `packages/core/src/session/runner/max-steps.ts`：达到 agent 的 `steps` 上限后关闭工具，注入 `MAX_STEPS_PROMPT`，强制模型用文本总结。
- `packages/core/src/session/subagent-completion.ts`：子代理结束时向父会话注入一条 `<subagent ...>` synthetic 用户消息，父会话因此被重新唤醒。
- 输出截断：`llm.ts` 对 `length` 续写最多两次，第三次报 `output-limit`。

结论：opencode 不判断“用户要求是否语义满足”，它只判断“这个回合是否还有工具工作/待处理输入”。真正的任务完成由模型停止调用工具并给出最终文本表达；跨回合靠 inbox 与 synthetic 消息续接。

### 2.2 DSH：持久 Goal + 自动续轮

参考安装包：`DeepSeek Harness`（Electron `app.asar`）中的以下包：

- `@deepseek-ai/dsh-goal`
- `@deepseek-ai/dsh-goal-round-driver`
- `@deepseek-ai/dsh-tool-goal`
- `@deepseek-ai/dsh-agent-loop`

行为要点：

1. 每个会话最多一个持久 Goal，状态为 `active/paused/blocked/complete`，带 `roundsStarted/maxGoalRounds`，默认上限 256。
2. 自动续轮驱动只在“agent 完全空闲、continuation armed、轮次未用完”时排队一轮 `<goal_round>`，提示中包含目标与 `round/maxGoalRounds`。
3. 完成/阻塞由模型通过 `update_goal` 显式声明：
   - 只有目标真正达成才 `complete`；
   - 同一阻塞条件至少连续 `blockedAfter` 轮才允许 `blocked`；
   - 难度、不确定、仍有剩余工作都不算 blocked；
   - 达到轮次上限时由驱动写入 `round-limit` 阻塞。
4. 人类输入优先于自动续轮；恢复/分叉后的 Goal 默认 disarmed，必须显式 resume。
5. 没有独立评估器；模型是完成/阻塞的权威，评测器留作后续策略层。

结论：DSH 用“持久目标状态 + 自动轮次 + 模型显式收尾 + 轮次/重复阻塞上限”解决“模型说没完成但没人再发起一轮”的问题。

## 3. AgentMesh 的适配

AgentMesh 的执行单位是任务图而不是聊天回合，因此把两者结合：

- **一轮** = 一次任务图执行 + 主节点汇总；
- **主节点汇总** = opencode 的“最终文本/结束信号”；
- **自动续轮** = DSH 的 Goal round driver；
- **完成判定** = 主节点语义判断 + 控制平面确定性安全检查。

### 3.1 持久状态

`runs` 表新增：

| 字段 | 含义 |
| --- | --- |
| `round_number` | 当前轮次，从 1 开始 |
| `max_rounds` | 本运行允许的总轮次（含首轮） |
| `goal_status` | `active / complete / blocked / awaiting_user` |
| `blocked_reason` | 阻塞代码与说明，如 `round-limit: ...` |

每轮结束还会写入：

- `run.summary.rounds[]`：轮次、结论、验证、风险、下一步、未解决项、阻塞签名/连续次数；
- `<项目>/.agentloop/runs/<run_id>/rounds/round-N.json`：该轮汇总与判定的完整快照；
- 审计事件 `round.continued / round.completed / round.blocked / round.plan_appended / round.resumed`；
- Context Bus `workflow` 事件（含 `round`、`goal_status`、`unresolved`）；
- 统一记忆决策记录。

### 3.2 判定规则

主节点汇总新增可选字段：

```json
"goal_status": "complete | continue | blocked",
"blocking_reason": "仅 blocked 时填写具体条件"
```

判定顺序：

1. **complete**：当前轮任务全部 `completed`，无失败/阻塞，无验证 `failed`，主节点 `merge_recommendation=approve`，且没有声明 `blocked/continue`。
2. **continue**：未满足 complete，轮次未达上限，且不存在“同一阻塞签名连续达到阈值”。
3. **blocked**：
   - 轮次达到 `max_rounds` → `round-limit`；
   - 同一未解决签名连续出现 `blocked_after_rounds` 轮 → `repeated-blocker`；
   - 主节点显式声明 blocked 且同一条件已连续达到阈值 → `model-blocked`；
   - 无法生成合法的下一轮计划 → `round-planning-failed`。

“当前轮任务”指本轮新生成的 `R<n>_*` 任务。首轮使用全部任务。这样首轮的失败任务不会永久阻止修复轮完成；修复轮通过后，旧失败行仍保留在历史中用于审计，但不再参与完成判定。

### 3.2.1 主节点汇总缺失

GUI 主节点可能因为 CDP 未就绪、应用未启动或超时写不出 `summary.json`。此时：

- **当前轮存在失败任务/验证失败**：控制平面根据任务错误、结果包 `unresolved_items`、验证报告生成失败汇总（`reject` + 可执行 next_actions），并按正常轮次判定继续下一轮。这样不会因为“汇总这一步挂了”而丢掉已经获得的失败证据。
- **当前轮任务全部完成、验证通过，但汇总缺失**：不静默当作成功，也不直接 failed；运行进入 `waiting_user`，`goal_status=blocked`，代码 `summary-unavailable`，提示恢复主节点后重新汇总。
- `multi_round` 关闭时保持旧行为：汇总缺失即 failed。

### 3.3 下一轮如何产生

`finalize_summary()` 判定为 continue 后：

1. **主节点增量规划**（默认开启）：把原始目标、上一轮汇总、未解决项、失败任务、验证失败、轮次历史交给主节点，要求只规划关闭未解决项的最小任务图。新任务 ID 自动加 `R<n>_` 前缀。
2. **回退计划**：主节点增量规划失败、没有可写任务或合并校验失败时，生成最小修复任务：
   - `R<n>_T001`：可写任务，scope 取上一轮失败/可写任务的 scope，依赖上一轮可写任务；objective 明确列出未解决项；
   - `R<n>_REVIEW`：主节点复审，必须读取文件并给出逐项关闭证据。
3. 新任务追加到同一计划、同一运行；新任务依赖上一轮任务，现有 `_apply_upstream_patches` 会把上一轮补丁组合进新任务 worktree，保证修复基于上一轮成果。
4. 轮末会把依赖“失败/阻塞”任务的 queued 后代统一标记 `blocked`，避免运行因为残留 queued 任务停在 paused 而不进入主节点判定。
5. 同一 run ID 继续执行，记忆、Context Bus、任务历史、审批和补丁链路天然共享。

### 3.4 合并规则

同一文件在相邻轮次被重复修改是正常修复行为。合并预检原来禁止任意两个任务改同一文件；现在只放行：

- 下游任务 ID 形如 `R<n>_...`；
- 下游与上游轮次不同；
- 下游任务确实依赖上游任务。

同轮任务重叠、普通计划内无依赖重叠仍然拒绝。

### 3.5 用户恢复

被 `round-limit` / `repeated-blocker` 阻塞后：

- 运行状态为 `waiting_user`，不会创建验收审批；
- 用户点击“继续运行”或调用 `resume` 时，会把 `goal_status` 复位为 active、清除阻塞，并把最大轮次增加一轮 `max_rounds` 配额；
- 历史轮次保留，最后一轮的连续阻塞计数清零，允许换一种修复方案再试。

## 4. 配置与界面

`HubConfig` 默认：

```python
multi_round = True
max_rounds = 3
blocked_after_rounds = 2
round_replan = True
```

- WebUI 第 3 步新增「多轮自动续跑」复选框，默认勾选，可填 1..20 轮；
- 与「完全控制」一样持久化到 `<项目>/.agentloop/config.json`；
- `GET /api/settings` 返回全部字段；
- `POST /api/settings/multi_round`：`{"enabled": true, "max_rounds": 3}`；
- 运行卡片显示“第 N / M 轮 · goal_status”，阻塞时显示原因；
- 关闭后恢复旧行为：一轮结束直接进入验收/合并门禁。

## 6. 边界

- **模型仍是完成语义的权威**：DSH 明确没有独立评估器；AgentMesh 也由主节点决定“是否真正满足用户目标”。控制平面只做确定性反证（任务失败、验证失败、结构性缺失），不能替代语义验收。
- **轮次不是 token/时间预算**：`max_rounds` 只限制自动轮次，不限制费用；GUI Agent 每轮仍可能很慢，预算与熔断继续独立生效。
- **重复阻塞签名依赖文本**：未解决项文本完全一致才判定重复；如果每轮换一种说法，可能直到轮次上限才停止。这是有意的保守设计。
- **真实 GUI 多轮的耗时**：两轮探针涉及真实 Trae/WorkBuddy 应用，单轮可能数分钟；自动化测试用真实子进程 mock Agent 覆盖控制平面，GUI 场景以实际日志为准。
- **合并重叠放行仅限修复轮**：同轮或普通计划内重叠仍按原规则拒绝，避免放宽为任意冲突合并。
