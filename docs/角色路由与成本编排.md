# 角色路由与成本编排（Role Routing & Cost Orchestration）

- 版本：v1（2026-11-04）
- 关联需求：`01-需求整理-v1.docx` 模块 4（Task Scheduler）、模块 5（Capability Router）、模块 6（Cost Optimizer）、S6（结果同步）
- 关联代码：`agentloop_hub/control/roles.py`、`segment.py`、`aggregate.py`、`runner.py`、`hub.py`、`storage/repo.py`

---

## 0. 一句话

**一条用户需求进来，先被规则切成 1–4 个"带角色"的任务，每个角色按一条预先声明的
"(成本档位, Agent, 模型) 阶梯"从本机真实模型目录里取第一个可用候选并钉死，
执行失败时沿阶梯前进升级，最后由控制平面把各任务成果包压成一份可读答案。**

这件事原来分散在两个地方，而且都只停留在"提示词约束"层面：

| 来源 | 形式 | 能做到 | 做不到 |
| --- | --- | --- | --- |
| OpenCode `agent` 块 | JSON 配置 | 角色 → 模型 / 工具权限 / 温度；隐藏系统角色（compaction/title/summary） | 没有成本档位、没有预算、没有失败升级、切分靠主模型 |
| DSH `AGENTS.md` | Markdown 策略 | 角色路由表、成本优先级、升级条件、"禁止行为"、委派契约 | 只是写给模型看的散文，执行器不校验；模型名与真实目录可能脱节 |
| AgentMesh（本实现） | 结构化策略 + 控制面 | 以上全部 + 真实模型校验 + 预算前置 + 升级审计 + 结果汇总 | 规则切分有置信度上限，复杂需求仍可回退到 LLM 规划 |

## 1. 从 OpenCode 学到什么

`~/.config/opencode/opencode - 副本 (4).json` 的结构是"**默认模型 + 角色覆盖**"：

```json
{
  "model": "llm-local/Qwen3.8-27B-...gguf",
  "small_model": "llm-local/Qwen3.8-27B-...gguf",
  "agent": {
    "build":     {"model": "llm-local/Qwen3.8-27B-...gguf"},
    "explore":   {"mode": "subagent", "model": "llm-local/...", "tools": {"write": false}},
    "research":  {"model": "deepseek/deepseek-v4-flash", "tools": {"write": false}},
    "writer":    {"model": "deepseek/deepseek-v4-flash", "prompt": "科研论文专家…"},
    "compaction":{"model": "volcengine-agent-plan/glm-latest", "tools": {"write": false}},
    "plan":      {"model": "volcengine-agent-plan/glm-5.2"},
    "reviewer":  {"model": "volcengine-agent-plan/glm-latest"}
  }
}
```

三个可以直接借的点：

1. **角色 = 模型 + 权限 + 温度 + 专属提示词**，不是一个模型包打天下；
2. **角色有"只读/可写"的硬边界**（`tools.write=false`），不是靠模型自觉；
3. **系统角色也是角色**（compaction / title / summary 明确指到强模型），说明"压缩上下文"本身就是一笔要计价的调用。

AgentMesh 的 `Role` 保留了这三条，并补上成本档位与候选阶梯。

## 2. 从 DSH `AGENTS.md` 学到什么

`~/.dsh/AGENTS - 副本.md` 是一份**路由策略文档**，它的价值不在格式，在于四条规则：

1. **成本优先级阶梯**：主 Agent 直接做 → 本地免费 → flash/flashx → glm-5.3 → pro；
2. **明确的升级条件**：只有"信息冲突、问题复杂或 Flash 无法可靠解决"才升级；
3. **禁止行为清单**：不重复启动相同子 Agent、不把完整父会话塞给不需要的任务、不用白名单外模型；
4. **委派契约**：目标 / 输入范围 / 禁止事项 / 期望输出 / 验收标准 / 是否可写 / 是否前台等待。

AgentMesh 把这四条变成代码：

| DSH 规则 | 实现 |
| --- | --- |
| 成本优先级 | `Role.ladder`：有序 `(tier, agents, models/model_class)`，`tier 0..4 = local/free/cheap/standard/premium` |
| 升级条件 | `RunService._escalate_task()`：仅在该任务重试时触发，只向前走，不回头、不重复同一候选，写 `task.escalated` 审计 |
| 禁止行为 | 切分器最多 4 个任务；`max_premium_tasks_per_run`；`limits[agent].max_tasks_per_run` |
| 委派契约 | `PromptBuilder` 的任务包字段（scope / out_of_scope / 验收 / 验证命令 / 成果包 schema）本来就齐 |

## 3. 数据流

```text
用户一句话
   │
   ▼
Segmenter（规则，无 LLM）            control/segment.py
   │  意图/路径/是否提问 → 角色序列（最多 4）
   ▼
RolePolicy.resolve(role)             control/roles.py
   │  阶梯 × 真实模型目录 → 候选列表（含 tier）
   ▼
预算裁剪（premium / 每 Agent 限额）   hub.solve()
   │  超预算 → 降到更便宜的档位，并记录原因
   ▼
TaskSpec.role + TaskSpec.model       models.py / tasks 表
   │  模型从"Agent 属性"下移到"任务属性"
   ▼
RunService（DAG、Worktree、验证）      control/runner.py
   │  钉住的 Agent 优先，失败按阶梯升级
   ▼
Aggregator（确定性）                  control/aggregate.py
   │  成果包 digest → answer.md/json + 成本分布
   ▼
用户看到的最终答案（可选强模型润色）
```

### 3.1 为什么切分必须确定性

规划是"最便宜也最贵"的环节：一次规划调用在跑任何活之前就花掉积分，而一个非法
`plan.json` 还要再花一轮修复。规则切分：

- 零模型调用，毫秒级；
- 结果可解释（`signals.intents` / `paths` / `reasons` 全部输出）；
- 低置信度时**如实报告**（`confidence`），而不是猜。

`Segmenter` 的判定顺序：

```text
question?  → 只读 explore（不产生写任务）
design + implement? → plan → implement → verify
implement?          → [explore（未点名文件时）] → implement → verify（有测试命令时）
review?             → review
docs?               → write
explore/research?   → explore / research
其它                → explore（安全只读兜底）
```

### 3.2 角色与默认阶梯

| 角色 | 任务类型 | 可写 | 阶梯（从便宜到贵） |
| --- | --- | --- | --- |
| `explore` | analysis | 否 | local → free → cheap |
| `research` | analysis | 否 | free → cheap → standard |
| `implement` | implementation | 是 | free → cheap → standard → strong |
| `review` | review | 否 | cheap → standard → strong |
| `plan` | architecture | 否 | cheap → standard → strong |
| `write` | documentation | 是 | free → cheap → standard |
| `verify` | verification | 否 | cheap → standard → strong |
| `summarize` | analysis | 否 | standard → strong |

每条阶梯的每一档只写"**意图**"（`model_class: ["free"]` 或 `model_match: ["*flash*"]`），
最终落地一定是本机目录里的真实名字。本机解析示例（2026-11-04 实测）：

```text
explore  → tier0 opencode/qwen-local/Qwen3.8-27B-UD-Q8_K_XL.gguf
implement→ tier1 opencode/opencode-go/beam-free
review   → tier2 opencode/opencode-go/deepseek-v4.1-flash
summarize→ tier3 opencode/opencode-go/glm-5.3
```

### 3.3 会话级钉模型（本项目的核心诉求）

```bash
agentmesh solve "修复 calc.py 的加法错误" \
  --executor qoder_cn:DeepSeek-Flash \
  --commander workbuddy:deepseek-v4-pro
```

- `--executor` 插到 `explore / research / implement / write / verify` 阶梯**最前面**
  —— 用你已经在付费（或免费额度）的通道干活；
- `--commander` 插到 `plan / review / summarize` 最前面 —— 强模型只做决策与汇总；
- 钉住的模型必须在该 Agent 的真实目录里，否则直接 `ValidationError`，不会静默忽略。

### 3.4 任务级模型（关键改造）

改造前：模型挂在 Agent 上（`agents.extra.selected_model`），所以"同一个 Agent 用两个模型"
做不到，`configure_chain` 甚至会直接报错。

改造后：

- `TaskSpec.model` / `TaskSpec.role`（`models.py`）；
- `tasks` 表新增 `role` / `model` 两列（`SCHEMA_VERSION = 4`，`_ensure_columns` 增量迁移，
  老库无损升级）；
- `RunService._model_for_agent(agent, task)` 先看任务，再看 Agent 默认值；
- `RunService._pinned_agent(task)`：任务带模型且指定了 Agent 时**跳过通用路由**，
  防止路由器把钉住的便宜 Agent 换成贵的。

### 3.5 失败升级

```text
attempt 1: qoder_cn / DeepSeek-Flash        (tier 2)
   ↓ 失败（超时/退出码/成果包不合法/验证不通过）
attempt 2: opencode  / claude-haiku-5-5     (tier 2, 同档其他通道)
   ↓ 仍失败
attempt 3: opencode  / deepseek-v4-pro      (tier 4)
```

规则：

- 只在该任务重试时升级，且**只向前**（不回到更便宜的档位）；
- 同一候选不重复；
- 升级写入 `audit`（`task.escalated`）与 Context Bus（`task_state.phase=escalated`）；
- 升级后任务的 `assigned_agent` / `model` 都会更新，`run_bindings` 能看到最终归属。

### 3.6 预算前置

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `premium_tier` | 3 | 从第几档算"贵"（3=standard 起算） |
| `max_premium_tasks_per_run` | 2 | 一次运行最多几个贵任务 |
| `limits.<agent>.max_tasks_per_run` | 无 | 单个 Agent 在一次运行里的任务上限 |

超预算时**不报错**，而是选下一个候选并标记 `downgraded=true` + `notes` 写明原因。
理由：宁可降级也别让用户的需求卡住；降级本身是可审计的事实。

      "write": true,
      "ladder": [
        {"tier": 2, "agents": ["qoder_cn"], "models": ["DeepSeek-Flash"]},

### 4.1 导入现有配置

```bash
agentmesh roles import "C:/Users/<user>/.config/opencode/opencode - 副本 (4).json" --save
agentmesh roles import "C:/Users/<user>/.dsh/AGENTS - 副本.md" --save
```

解析规则：

- OpenCode：读 `agent.*.model`，按 `build→implement / explore→explore / research→research /
  writer→write / plan→plan / reviewer→review / compaction|title|summary→summarize` 映射；
- DSH：只认 `### Role` 标题下的反引号 `provider/model` 片段，不猜自由文本；
- 两边都会把模型串按"全名 → 去 provider 前缀 → 末段 → 唯一子串"匹配本机目录；
- **匹配不到就进 `unmatched`，绝不虚构**（本机实测：`llm-local/Qwen3.8-27B-BF16-...gguf`
  与 `volcengine-agent-plan/glm-latest` 都落进了 `unmatched`）。

## 5. 结果汇总

`control/aggregate.py` 完全不调用模型：

- 输入：每个任务的 `ResultPackage`（summary / findings / files_changed / tests / risks /
  unresolved / token_usage）；
- 输出：`answer.md` + `answer.json`；
- 结构：结论 → 分阶段结果（agent/model/tier/验证/tokens）→ 变更文件 → 未解决项 →
  建议下一步 → 成本与模型分布；
- token 为 0 时写"未上报"，**不做估算填充**（Qoder CN 的 GUI 通道确实不回传用量）。

`polish=true` 时追加一次 `summarize` 角色调用，把确定性摘要改写得更像人话；
失败则原样返回确定性版本（`apply_polish` 只在前面加一节，原文作为附录保留）。

## 8. 边界与已知限制

- **切分是规则，不是理解**：`confidence < 0.5` 时仍会执行（走 explore 只读兜底），
  需要更强切分时应改用 `PlanningService`（主模型出 `plan.json`），两者共用同一套
  角色/模型基础设施。
- **阶梯依赖目录质量**：模型名是 `classify_model` 猜的类别（`free/flash/pro` 等词面特征），
  如果某个通道命名不规范，就会被分到 `standard`；这种情况应在 `roles.json` 里显式写
  `models: ["..."]` 覆盖。
- **升级不等于更强**：阶梯由策略作者定义顺序，默认阶梯按成本递增，但"同档其他通道"
  未必更强；需要严格意义上的"更强"时请在策略里显式排序。
- **premium 预算是软约束**：所有候选都超档时仍会选最便宜的那个并标记 `downgraded`，
  不会让任务失败。
- **GUI Agent 的可执行性依赖环境**：Qoder CN 的零输入通道需要应用可被拉起并暴露 CDP；
  受限沙箱可能拦截其内部调用的系统程序（本轮出现过 `PROGRAM BLOCKED BY SECURITY POLICY`
  噪声，但运行本身已完成）。

## 9. 能力路由画像与美元闭环（2026-11-10）

### 9.1 能力项不再是常量

`CapabilityRouter._score` 的能力项原为常量 1.0（能力门槛已在 eligibility 阶段强制），
导致"能力"权重 0.40 对所有人相同，最终由访问等级/字典序决胜。现改为
`_capability_score(agent, spec, type_stats)`：

- **specialization**：任务类型签名能力（`TASK_SIGNATURE_CAPABILITY`，如 implementation→
  code_generation、review→code_review、research→web_search）若被 Agent **显式声明**得 1.0，
  仅派生得 0.7，缺失得 0.5——显式声明的专家（如 Claude Code 声明 code_generation）排在仅派生者之前；
- **type fitness**：`_agent_type_stats` 按 (agent, task_type) 聚合历史完成/失败，拉普拉斯平滑 +
  样本强度置信度；无该类型历史时用中性 prior。随着真实任务积累，按类型实测成功率主导；
- `capability = 0.5*specialization + 0.5*fitness`；breakdown 暴露
  `capability_specialization / capability_type_fitness / type_tasks_total`，可解释。

这实现了需求 M5"实时评估能力并按任务类型选人"的方向：能力分随类型与历史变化，而非恒定。

### 9.2 美元节省入账

- 价格以用户 `pricing` 为权威（官方价格表/账号账单）；内置 `DEFAULT_PRICING` 仅含无歧义免费模型（0），
  付费价格不臆测（公开来源按日期/分时矛盾、旧别名已退役），内置与用户表均无的模型记
  **unknown（cost_known=False）而非 free**。
- `CostOptimizer.usd_saved(tokens, model)` 按 **input 价**估算避免发送上下文 token 的美元价值
  （压缩/复用节省的是输入侧）；未知价返回 0，token 仍入账。
- `compress_context`（带 model 参数）、`intermediate_hints`、runner 的 intermediate_reuse 与
  exact_cache 调用 `record_saving(..., cost_saved=...)`，savings_ledger 同时累计 token 与美元。
- 边界：美元为估算非精确账单；语义缓存已升级为本地向量语义（见 §9.3）。

### 9.3 真·语义缓存（本地嵌入，2026-11-10）

- `control/embeddings.py` 加载本机 EmbeddingGemma-2（768 维，torch+transformers，mean-pool + L2）；
  `semantic_cache` 表新增 `embedding` 列（JSON 向量，自动迁移）。
- `semantic_reference/store` 用余弦相似度（`semantic_cache_embedding_threshold`，默认 0.85）；
  嵌入文本只含意图（objective + 验收条件）——scope 由 file_hash 基线保证、type 单独过滤，
  避免共享 scope 抬高无关任务的相似度（实测修正前会误命中）。
- 旧行无向量时按 objective 补算并回写；模型/依赖不可用时回退词袋 Jaccard 并标注 `method`。
- 实测：中文改写 0.9551，无关任务 0.6882；缓存命中 0.9582（embedding）。配置项见用户手册 11.4。
